## What it means

An `interface` entry names at most one binding. An entry naming two is
refused outright, before anything else about it is even looked at — a shape
failure, not a decision about whether the node or port it names exists. An
entry naming none is not a failure either: it is an unbound entry, stored
with the schema and data type it declares, and read back with an empty list
of bindings. That is what lets an author publish the interface first and
build the inside later.

That shape check happens before the workflow is validated, so it answers a
different question than validation does. A binding whose node or port is
made up entirely is not caught here — it is caught by the same check that
would catch it on a directly-stored port array, and answered with a different
status. The API's own refusals stop at the entry's shape; whether what it
points to is real is somebody else's answer.

## Example

```http title="An entry naming the same binding twice" verdict="400 refused"
POST /api/flowdrop/workflows

{"name": "Over-bound", "nodes": [ … ], "interface": {"inputs": [
  {"id": "numbers", "bindings": [
    {"nodeId": "calc1", "portId": "values"},
    {"nodeId": "calc1", "portId": "values"}
  ]}
]}}
```

```http title="An unbound entry, alongside one that is bound" verdict="201 stored"
POST /api/flowdrop/workflows

{"name": "Interface first", "nodes": [ … ], "interface": {"inputs": [
  {"id": "topic", "dataType": "string", "schema": {"type": "string"}, "bindings": []},
  {"id": "numbers", "bindings": [{"nodeId": "calc1", "portId": "values"}]}
]}}
```

```http title="An entry whose binding names a node that does not exist" verdict="422 refused"
PUT /api/flowdrop/workflows/{workflow}

{"name": "Ghost", "interface": {"inputs": [
  {"id": "numbers", "bindings": [{"nodeId": "ghost_node", "portId": "values"}]}
]}}
```

The unbound entry is stored: the response's `interface.inputs` names both
`topic`, with `"bindings": []`, and `numbers`.
