## What it means

A resolved value is validated exactly as a JSON Schema validator would validate
it, and a `null` is no exception. `null` is a type of its own: it passes
`"type": "string"` no more than a number would, and it passes only a schema
whose type admits it, such as `["string", "null"]`. A parameter that is meant
to accept "nothing chosen" says so in its schema.

What a `null` is spared is only what JSON Schema spares it: a minimum length, a
pattern or a `format` describe strings, so they have nothing to say about a
`null`. `enum` is different: a `null` passes it only where the enumeration
lists `null`.

Every value is checked, and a failure names all of them: each parameter whose
value failed, with each constraint it failed, in no particular order. An author sees
every problem at once, and the answer is the same in every language and whatever
order the parameters were declared in. Only `type` and `enum` cut a value's check
short, because the other constraints mean little for a value of the wrong type or
outside the list.

A parameter that nothing supplied at all is not validated here. It has no
value, and CFG-9 has already decided whether that is allowed.

## Example

```json title="A schema that admits null, with an enum that lists it"
{ "type": ["string", "null"], "enum": ["low", "high", null], "minLength": 3 }
```

```json title="What resolving an explicit null against it returns" verdict="valid"
null
```

The same `null` against `{ "type": "string" }` fails the node with a `type`
violation.
