## What it means

A dynamic port definition has a `name` and a `label`, and says what the port
carries in one of two ways. A `dataType` names a lane, and the port gets the
JSON Schema type that lane stands for (DYN-8). A `schema` describes the port
fully, with anything a node type's own port schemas can say, and then it is
the port: its lane comes from it the way any property's does. With neither,
the port is `mixed` and accepts any value.

Because a `schema` can say everything a node type can, an author can describe
a node's ports without any processor declaring them, wire a workflow against
them, and later switch the node to a processor that declares the same ports.

A dynamic parameter also says what kind of parameter it is, with the same gate
flags a declared one carries: `connectable` makes it an input a wire can feed,
`configurable` makes it a setting the author fills in, and both together give a
setting a wire can override. Like any parameter, a flag left out is off.

An authoring surface never records a control lane for a dynamic port: a
dynamic port is a value port by definition.

## Example

```json title="Two dynamic parameters: an input by lane, a setting by schema" verdict="accepted"
[
  { "name": "topic", "label": "Topic", "dataType": "string", "connectable": true },
  { "name": "limit", "label": "Limit", "configurable": true,
    "schema": { "type": "integer", "minimum": 1, "maximum": 50, "default": 10 } }
]
```

`topic` is an input that accepts any string. `limit` is a setting in the node's
config form, accepts an integer from 1 to 50, and is 10 until the author changes
it.
