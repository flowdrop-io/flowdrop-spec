## What it means

A site's stored lane configuration is read as a set of edits on top of the
vocabulary beneath it, never as the whole vocabulary. A lane the site never
mentions is not missing from what gets served: it is carried over exactly as
composed. The only exception is ordering: unmentioned lanes are appended after
the stored ones, so a site's own ordering choices still show first.

Compatibility rules travel with the lane entry that declares them. That is what
keeps a lane shipped after the site saved its configuration usable: it reaches
the site with every rule it declares, in both directions, because nothing the
site stored replaced its entry. The same reading tells a site how to drop a rule
it disagrees with: redefine the entry that declares it. Leaving a rule out of
some other entry removes nothing.

## Example

A site recoloured `string` and added a lane of its own, before a `messages`
lane existed in the shipped vocabulary:

```json title="A site's stored lane configuration" verdict="stored"
{
  "version": "0.9.0",
  "dataTypes": [
    { "id": "string", "name": "Text", "description": "Recoloured by the site.", "color": "rebeccapurple", "category": "basic", "enabled": true },
    { "id": "site_custom", "name": "Site Custom", "description": "A type only this site declares.", "color": "var(--fd-node-slate)", "category": "basic", "enabled": true,
      "compatibility": [{ "from": "site_custom", "to": "string" }] }
  ]
}
```

Serving this recolours `string` and keeps `site_custom` and its rule, exactly
as stored. It also serves `messages`, a lane the stored value never mentions,
with the one-way rules into `array` and `json` that the shipped `messages`
entry declares.
