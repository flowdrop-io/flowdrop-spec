## What it means

"Missing" is narrow on purpose. The parameter got nothing from a wire or from the
launch, nothing from the author's configuration, and has no default. A `null` that
somebody did send, or that the node type records as its default, was chosen. It is
resolved and checked like any other value, and the parameter's schema decides
whether it is acceptable (CFG-10).

The skip looks exactly like a BR-7 skip from outside: the same reason on the skip
event, the real-time status and the snapshot, and the node counted among the run's
skipped nodes. What follows needs no rule of its own. A node that reads from the
skipped node never becomes ready (DATA-4), and BR-7's end-of-run sweep records it as
skipped too. A node that does not depend on it runs as usual.

BR-7 says a node with no incoming trigger edge is never skipped for want of a
trigger. That is about trigger edges only: it does not promise the node runs whatever
else happens, and the sweep already covers a node that was ready but never executed.

## Example

A workflow with two trigger nodes, `on_insert` and `on_update`. A firing of the update
trigger supplies only `event:on_update`:

```json title="The initial data the firing delivers" verdict="delivered"
{ "on_update": { "event": { "ref": "node/42", "changed_fields": ["body"] } } }
```

```json title="The skipped nodes in the run's response metadata" verdict="skipped"
["on_insert", "notify_new_article"]
```

```json title="The run's status" verdict="completed"
"completed"
```
